# Platform audit — issue register (2026-11-02)

Branch `feature/platform-hardening`. Every issue below was found by the
feature-by-feature tests, the browser sweep, the database checks or the
platform log they produced, and **none of them has been fixed**: this is the
list to work through together in the next phase. What *was* changed in this
phase (the logging system, and the hardening listed at the end) is not an
issue here.

How it was found:

- **Tests**, against a local panel (:3010) and site (:3011) on the local
  database (never production): unit 73/73, API 90/90 plus one known-issue `todo` (AUD-12), browser 16/16 (45 screens swept).
  New suites: `logs.test.ts` (the log itself), `customer-dashboard.test.ts`
  (every customer feature with invalid inputs and a second customer probing
  isolation), `site-public.test.ts` (the public site's own server),
  `sweep.spec.ts` (every customer page and console screen in a browser,
  recording console errors and failed requests).
- **The platform log** of that run, summarised by `scripts/log-report.mjs`
  (`docs/audit/log-report-2026-11-02.md`): 5,216 lines between 02:09 and 02:21 UTC on 2026-11-02 (0 exceptions, 0 error lines, 0 possible leaks).
  Request ids below are in the local log files (`.demo/.data/logs`,
  `web/.data/logs`) and open in System › Logs.
- **Read-only checks**: `PRAGMA integrity_check` and `foreign_key_check`,
  ledger balance, plan and project consistency on the local database; three
  public `GET`s against production (no sign-in, no writes).

Severity: **High** loses data, breaks a feature for real users or exposes
something; **Medium** misbehaves or will hurt as the platform grows; **Low**
is cosmetic, dev-only or hygiene.

**Status** (on this branch, not deployed): every issue has been worked
through. Fixed: AUD-01 to AUD-13, AUD-15, AUD-17. Not an issue on a second
look: AUD-14 (the cookie is already httpOnly) and AUD-19 (Nuxt DevTools
inside the frame, development only). Accepted as it is, with the reason:
AUD-18. Each section ends with what was done and how it was checked.

## AUD-01 — Footer links to pages that do not exist, including the legal ones (High)

- **Where:** `web/app/data/routes.ts` and the footer document; production
  `https://apexdigi.co.uk`.
- **What happens:** the footer on every page links to `/careers`,
  `/legal/privacy`, `/legal/terms`, `/legal/instalment-terms`,
  `/legal/cookies`, `/legal/complaints` and `/legal/accessibility`. All seven
  answer **404** in development and in production (checked with `GET`).
- **Log:** `site:http.request GET /legal/… → 404` lines (warn) in the site log.
- **Why it matters:** the contact form collects names, emails and phone
  numbers with no reachable privacy notice, and the instalment offer has no
  reachable terms. Known since phase D as "the footer links to seven pages
  the site does not have"; still true.
- **Likely cause:** the pages were planned (`routes.ts` names them) and never
  written; the legal text has to come from the business (`TODO(legal)`).
- **Also found while fixing:** the same dead addresses were linked from the
  service pages ("Read the full terms" → `/legal/terms` or
  `/legal/instalment-terms`) and the About page ("See open roles" →
  `/careers`). A crawl of the whole site found those three and nothing else.
- **Fixed:** a link to one of these addresses renders only once a page
  exists there (`usePageExists()` in `web/app/composables/useCmsBuilt.ts`: a
  route of the site's own, or an address in the published manifest), in the
  footer, the service plans and the About team card; a footer column with no
  links left is not drawn. `legal` is no longer a reserved first segment
  (`web/shared/cms/documents.ts`), so the business can publish each document
  in the console as a built page at the address the site already links to.
  The text itself is still the business's to write: until then the footer
  has no Legal column and the contact form still has no privacy notice.
- **Checked:** a crawl of every page reachable from the home page finds no
  link to a 404 (now a test, `site-public.test.ts`); publishing a page at
  `/legal/privacy` put the footer link on the site within a minute and
  removing it took the link away (by hand, local database); a page under
  `/legal/` can be built and published (`website-content.test.ts`).

## AUD-02 — Support actions notify every staff member one email at a time (High)

- **Where:** `.demo/server/utils/support.ts` `notifyTicketHandler()` →
  `.demo/server/utils/notify.ts` `notifyRoles()` / `notify()` (the `for … of
  emails` loop, `enqueueMail` per recipient) → `deliverNow()`.
- **What happens:** a request with no assignee and no project manager is
  announced to every active staff account holding `support.answer` (22
  locally, most of them test staff). For each one, an outbox row is created,
  claimed and marked, one after another: 22 × create, 22 × claim, 22 ×
  update. Creating a request, replying, resolving, reopening and asking for a
  call all took **3.5 to 8.5 seconds** and ran **50–54 queries**.
- **Log:** `POST /api/support/:id/reply` 8,256 ms, 54 queries (request `4c8534f6-6d83-4ef3-a458-3630e905e404`);
  `PATCH /api/support/:id` 7,324 ms, 53 queries (`5b7578b7-a54d-49f4-891b-b51d96ade8cb`);
  `POST /api/support/call` 6,666 ms, 54 queries (`cd5732e8-d003-496f-9e16-fb5a41a0cbf2`);
  `POST /api/support/create` 4,417 ms, 53 queries (`4049ef1e-f1f8-4386-807c-b35a7092d534`).
  The same pattern makes the staff broadcast slow: `POST /api/admin/notifications/broadcast`
  5,380 ms (`0c7347cd-b9f4-4149-8621-234848bc2846`). One reply in the first run broke down as
  `db.create MailMessage` × 22, `db.updateMany MailMessage` × 22, `db.update MailMessage` × 22.
- **Why it matters:** the time grows with the number of staff, every one of
  those writes takes SQLite's single write lock (see AUD-03), and with mail
  configured each delivery is also a call to the provider.
- **Likely cause:** per-recipient sequential writes (`create` in a loop
  rather than `createMany`), the fan-out to all holders when nobody is
  assigned, and delivery started from the request.
- **Fixed:** `notify()` renders the message once and writes every
  recipient's outbox row in one `createManyAndReturn`
  (`enqueueForEach()` in `server/utils/mail/outbox.ts`), with the reply-to
  address read once instead of per row; a link that cannot be built writes
  the rows FAILED in the same statement. `deliverNow()` marks every row
  "Mail is not configured" in two queries when the keys are unset, instead
  of claiming and marking each one. With mail configured each row is still
  sent one at a time, after the response, as before. The fan-out to every
  `support.answer` holder when nobody is assigned is unchanged: that is who
  should hear about an unowned request.
- **Checked** (same suites, same 22 staff accounts): support create,
  reply, resolve/reopen and call now take at most 538 ms and 9 queries
  over two full runs (were up to 8,256 ms and 54); the broadcast at most
  170 ms (was 5,380).

## AUD-03 — The database blocks readers behind writers (High)

- **Where:** the SQLite database (`prisma/dev.db` locally; production
  `/opt/apex/prisma/dev.db`, mode not checked there), `PRAGMA journal_mode`
  = `delete`, `busy_timeout` = 5000 ms.
- **What happens:** in rollback-journal mode a write locks the whole file
  for readers too. Single-row reads waited seconds behind concurrent
  writes during the test run.
- **Log:** `db.slow` lines such as `Ticket.findUnique took 4021ms` (request
  `364e6a29-d2e6-4dc1-95f1-cd5f9052e6d3`, a support thread that took 4,438 ms) and
  `Session.findUnique took 3912ms` (`e94f4f89-fcff-4b6a-a83d-f640036c6b11`: `GET /api/auth/me`,
  4,119 ms for two queries); 20+ single-row reads over 200 ms, all while a support
  fan-out (AUD-02) was writing.
- **Why it matters:** a read that waits longer than the 5-second busy
  timeout fails with "database is locked", which becomes a 500. AUD-02 makes
  long write bursts common.
- **Likely cause:** SQLite's default journal mode; WAL mode lets readers
  continue while one writer writes. To check on the production database
  before any change (read-only `PRAGMA journal_mode`).
- **Fixed:** `server/plugins/01.database.ts` switches the database to WAL
  at start-up and logs `db.journal-mode`; the mode is stored in the file,
  so it runs once. `*.db-wal` and `*.db-shm` are ignored by git. Backups
  and `sqlite3` use change with it: `docs/DEPLOYMENT.md` §15 (back up with
  `.backup`, never `cp` alone; run `sqlite3` as `apex`).
- **Checked:** the local database reported `wal` on the first start; over
  the full API run that followed there were **0** `db.slow` lines (were 84,
  up to 4,021 ms) and no "database is locked". Production was not read;
  the switch happens there on the first start after a deploy.

## AUD-05 — Project progress disagrees with its milestones (Medium)

- **Where:** `.demo/server/utils/finance.ts:317` (`collectKickoff`: `progress:
  Math.max(project.progress, 5)`), `.demo/server/api/orders/pay.post.ts:44`
  (`progress: 5`); the rule everywhere else is
  `.demo/server/utils/project-lifecycle.ts:46` (completed ÷ total).
- **What happens:** 20 projects in the local database show a progress figure
  that is not their completed-milestone share, e.g. 5% with one of six
  milestones done (17%), or 65% with two of five (40%).
- **Why it matters:** the customer's progress bar and the milestone timeline
  disagree on the same page (the inconsistency ADR-017 set out to remove).
- **Likely cause:** two writers of `progress`: kickoff and full payment set a
  fixed figure instead of recomputing from the timeline; older seeds set
  fixed figures too.
- **Fixed:** kickoff (`collectKickoff`) and full payment
  (`orders/pay.post.ts`) call `syncProgress()` after moving the timeline,
  so the fixed 5% only stands for a project with no milestones. A third
  writer turned up: the console's project form posts a typed progress
  figure; on a project with milestones a changed figure is now 409 and the
  field is read-only with a line saying it follows the timeline. Rows
  written before the fix are repaired by `scripts/sync-progress.mjs` (lists
  by default, `--apply` writes); locally it found 23 of 61 and fixed them.
- **Checked:** a new order kicked off through the real endpoints has the
  timeline's share as its progress; a typed 80% is 409; saving the form
  unchanged is 200 (`audit-fixes.test.ts`). **Production:** run the script
  without `--apply` first, after the deploy (DEPLOYMENT §15).

## AUD-06 — API errors say "Server Error" whatever the status (Medium)

- **Where:** 324 of 354 `createError({ statusCode, message })` calls in
  `.demo/server` (127 files) give no `statusMessage`.
- **What happens:** the JSON body of those errors carries
  `"statusMessage": "Server Error"`, on 400, 401, 403, 404, 409 alike. Checked
  in production: `GET /api/auth/invite?token=…` answers 404 with
  `"statusMessage": "Server Error"`. The browser console shows "404 (Server
  Error)".
- **Why it matters:** misleading for anyone reading a response or a console;
  monitoring that keys on the text will count them as server faults.
- **Likely cause:** the error handler's default text when none is given.
- **Fixed:** both apps' `server/plugins/00.logging.ts` wrap the h3 error
  handler and give an error with no `statusMessage` the standard reason
  phrase for its status (`node:http` `STATUS_CODES`) before the response is
  written. One place instead of 324 call sites; a message a route chose
  itself is untouched.
- **Checked:** a 400 and a 401 carry "Bad Request" and "Unauthorized" in the
  status line and the body (`audit-fixes.test.ts`); the browser sweep's 404
  lines now read "404 (Not Found)".

## AUD-07 — Hydration mismatches on time-dependent screens (Medium)

- **Where:** `.demo/app/pages/dashboards/support.vue:90–114` (`ago()`,
  message times with `toLocaleTimeString`, `Date.now()`).
- **What happens:** opening `/dashboards/support?ticket=<id>` and
  `/dashboards/settings?section=security` logs "Hydration completed but
  contains mismatches" (browser sweep, both runs). Settings › Security shows
  signed-in devices with their times, the same pattern.
- **Why it matters:** the server renders times in its own timezone and
  "x hours ago" at its own moment, the browser re-renders them in the
  visitor's; the visible time can jump, and Vue discards the server render
  for that part.
- **Likely cause:** time-dependent text rendered during SSR (the rule in
  CLAUDE.md: resolve such values in `onMounted` or `<ClientOnly>`).
- **Actual cause, found in the browser:** not the times. On the server the
  support page's thread load ran (`watch` with `immediate`) with a plain
  `$fetch` that carries no cookie, got a 401, and rendered an error toast
  ("This request did not load") that the client then could not hydrate.
  Settings › Security did not reproduce in the last three sweeps (its device
  list is already client-only). The sweep then caught a third screen,
  `/admin/tickets`: each row's "late" colour and the sort order came from
  `Date.now()`, so a request crossing its reply target between the server
  render and hydration flipped its class.
- **Fixed:** the support thread loads in the browser only, with both
  renders starting from the same skeleton (opening a thread also marks it
  read, which a server render should not do). The tickets screen measures
  waits against a clock that starts as the server's, carried in the payload,
  and becomes the browser's once mounted.
- **Checked:** the browser sweep records no hydration mismatch on any of
  its 45 screens. Left as they are, same pattern at day granularity: the
  credit decision-due colour (`admin/credit`) and invite expiry
  (`admin/team`).
- **Settings › Security came back** in the sweep while the Low issues were
  being fixed (one run in four). Its cause: the device list and two-step
  status are client-only fetches, but they were started from a
  `watch(..., { immediate: true })` during setup, which on the client runs
  before the hydration render and could put both cards in their loading
  state the server never rendered. They start in `onMounted` now; the
  section still loads both (checked in the browser).

## AUD-08 — "Import from site" gives up after 8 seconds (Medium)

- **Where:** the console's Import from site (`POST
  /api/admin/website/import`, `.demo/server/utils/website/content.ts`).
- **What happens:** while the site was busy (a cold start took 19 s for its
  home page), the import answered **502** "The public site did not answer
  (The operation was aborted due to timeout). Try again in a minute."
- **Log:** `panel:http.exception` and `POST /api/admin/website/import → 502` (request `943ea5b1-54d7-442e-bdbe-b9210c0b357f`, 01:47 UTC, first run, while `site GET /` took 18,999 ms). It did not recur in the clean run, where the site had been warmed first.
- **Why it matters:** the first import after a deploy is exactly when the
  site is cold. The message is honest, but there is no retry.
- **Likely cause:** an 8-second timeout on one call to the site's baseline.
- **Fixed:** `fetchSiteBaseline()` tries three times, 15 s each, waiting 1 s
  and then 2 s between tries, on a timeout, a dropped connection, a 5xx or a
  429; a 4xx is an answer and is not retried. Each retry is a
  `website.baseline.retry` warning in the log. The 502 and its wording are
  kept for when all three fail.
- **Checked:** the import still runs through it in `website-content.test.ts`.
  A cold site was not reproduced on purpose.

## AUD-09 — The editor preview is refused outside the build-time origins (Medium)

- **Where:** `web/nuxt.config.ts` (`frame-ancestors` from the production
  hosts, `localhost:3000` and `CMS_PANEL_ORIGINS`, read at build time).
- **What happens:** with the console on any other origin the editor's
  preview frame is blocked: "Framing 'http://localhost:3011/' violates …
  frame-ancestors …" (browser sweep, insight and case-study editors).
- **Why it matters:** moving the console (a new host name, a staging copy)
  silently breaks the preview until the site is rebuilt.
- **Likely cause:** the allow-list is fixed when the site is built.
- **Fixed:** `NUXT_CMS_PANEL_ORIGINS` (comma separated, `runtimeConfig.cms.panelOrigins`)
  is read when the site starts and added to `/preview/**`'s
  `frame-ancestors` by `web/server/plugins/preview-frame.ts` through
  nuxt-security's `nuxt-security:routeRules` hook. Moving the console needs
  a restart, not a rebuild. The build-time `CMS_PANEL_ORIGINS` still works.
- **Checked:** the dev pairing now passes the console's origin only through
  the run-time variable, and a real draft preview's CSP names it
  (`audit-fixes.test.ts`); the browser sweep has no frame-ancestors refusal.

## AUD-10 — Session rows are never cleaned up (Medium)

- **Where:** `Session` table; `.demo/server/utils/auth.ts`
  `startSession()`; no task prunes it.
- **What happens:** 497 sessions are unrevoked and unexpired locally (one per
  sign-in, tests included) and 14 expired ones are still unrevoked rows.
- **Why it matters:** Settings › Security lists sessions per account and the
  session middleware reads one per request; the table only grows.
- **Likely cause:** no retention rule (the outbox, enquiries and logs have
  one; sessions do not).
- **Fixed:** `pruneEndedSessions()` (`server/utils/auth.ts`) deletes rows
  that expired or were signed out more than 30 days ago, run daily at 03:29
  by the new task `sessions:prune` and logged as `task.sessions:prune`.
  Safe for any token still around: the session middleware refuses a token
  whose row is missing, as it refuses an expired one.
- **Checked:** rows ended 40 days ago are deleted and one ended two days
  ago is kept (`audit-fixes.test.ts`, through Nitro's dev task runner).

## AUD-11 — A profile photo can point at a missing file (Low)

- **Where:** `User.avatar` / `Attachment.avatarUserId`;
  `.demo/server/api/avatars/[userId].get.ts`.
- **What happens:** the dev customer's photo record exists but its file is
  not on disk. Every customer page asks for it and gets a 404 (15 times in
  the sweep); the initials fallback hides it.
- **Why it matters:** after a restore without the uploads directory, or a
  manual clean-up, every page view makes a failing request.
- **Likely cause:** the record and the file can drift; nothing reconciles them.
- **Fixed:** `GET /api/avatars/:userId` checks the file before serving it.
  When it is gone, the account's `avatar` is cleared (only if it still names
  that file), the row stops being the photo, a `avatar.file-missing` warning
  is logged, and the answer is the same 404. The next page shows the
  initials it was already showing, without asking.
- **Checked:** a photo row pointing at no file answers 404 once, and the
  account then has no photo (`audit-fixes.test.ts`).

## AUD-12 — The visit beacon answers 400 to a malformed body (Low)

- **Where:** `web/server/api/hit.post.ts:23`.
- **What happens:** a `POST /api/hit` with a body that is not JSON answers
  **400 "Invalid JSON body"**; the route says it always answers 204.
- **Log:** `site:http.request POST /api/hit → 400`, error "Invalid JSON body" (request `d209ef79-b7ea-42e3-95cd-45a6f920358e`; logged at debug because the beacon is a quiet path).
- **Actual cause:** not the route: nuxt-security's XSS validator reads and
  parses every POST body before the route runs, and its parse failure was
  the 400.
- **Fixed:** `xssValidator: false` on the `/api/hit` route rule. The route
  reads the body itself and keeps only a path it validates.
- **Checked:** the `todo` in `site-public.test.ts` is a real test now and
  passes (204).

## AUD-13 — The media library list has no paging (Low)

## AUD-14 — The customer session cookie is readable by script (Low, known)

- **Where:** `.demo/server/utils/auth.ts` `setAuthCookie()` (`httpOnly:
  false` for `auth_token`), tracked since ADR-013.
- **Why it matters:** an XSS would be able to read the session token. The
  staff cookie (`apex_admin`) is already httpOnly and SameSite=Strict.
- **Not an issue:** the cookie has been httpOnly since `5e22d31`
  (2026-07-21); the route guard already asks the server through
  `fetchUser()` instead of reading it. A sign-in answers
  `Set-Cookie: auth_token=…; HttpOnly; SameSite=Lax`. The register followed
  ARCHITECTURE §6 and §11, which still said otherwise; both are corrected.

## AUD-15 — Broken dev seed routes (Low, dev only)

- **Where:** `.demo/server/api/seed-rich.get.ts`, `seed-wallet.get.ts`
  (schema drift), `seed-support.get.ts` (verifies the session with a
  different secret, answers 500). All 404 in production.
- **On a second look:** all five verified the cookie with
  `process.env.JWT_SECRET || 'secret'` (the app signs with
  `runtimeConfig.jwtSecret`), so a real session failed in every one; their
  data was schema-valid. Each also made its own `PrismaClient`.
- **Fixed:** each takes the account from `requireAuth()` and uses the shared
  client; the order seeds set progress from each timeline (AUD-05); their
  Persian comments are in English (CLAUDE.md rule 10).
- **Checked:** all five answer 200 for a signed-in customer and 401 signed
  out, and the seeded progress matches the milestones (`audit-fixes.test.ts`).

## AUD-17 — An admin account without a staff role (Low)

- **What happens:** one `ADMIN` account in the local database has no
  `staffRole`; the guard treats it as Owner (the documented fallback).
- **Why it matters:** an account nobody chose to make an owner has an
  owner's access. To check production read-only.
- **Fixed, keeping the fallback** (CLAUDE.md rule 11: an unknown role falls
  back to owner, so nobody is locked out): the panel logs
  `security.staff-role-unset` at start-up with the accounts' ids, and Team &
  access shows such an account as "Not set (acts as Owner)" with a line
  asking for a role, so choosing Owner is a real change an owner can make.
- **Checked:** the team list marks a role-less account and still reports it
  as owner (`audit-fixes.test.ts`); the local start-up log names the one
  account. Production not read.

## AUD-18 — Rate limits are in memory (Low)

- **Where:** `.demo/server/utils/ratelimit.ts`.
- **What happens:** budgets reset when the process restarts and are not
  shared between processes. Fine for the single panel process today.
- **Accepted as it is.** The panel runs as one process, so the second half
  does not apply, and only a deploy restarts it, which an attacker cannot
  cause. Keeping blocks on disk would add writes and a file to manage for
  little gain. To revisit if the panel ever runs as more than one process;
  `ratelimit.ts` says where a shared store goes.

## AUD-19 — Inline-style CSP violations inside the preview frame (Low, dev)

- **Where:** the site's `/preview/:token` page inside the console's editor.
- **What happens:** the browser sweep recorded "Applying inline style violates
  the following Content Security Policy directive 'style-src 'self'
  'nonce-…''" twice per editor (insight and case-study), beside Nuxt
  DevTools' own cross-frame errors.
- **Why it matters:** if it is not only DevTools, some preview styling is
  being dropped. To check against a production build of the site before
  deciding it is dev noise.
- **Not an issue:** the preview opened on its own logs no violation, and its
  server HTML has no `style` attribute and no `<style>` element, so nothing
  the site renders needs an inline style. The violations appear only inside
  the console's frame, beside Nuxt DevTools' "Failed to check parent window"
  errors: DevTools styling itself across the frame. DevTools is not in a
  production build. Not checked against a production build of the site.
